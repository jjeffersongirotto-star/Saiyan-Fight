# AGENTS.md

## Project snapshot
This workspace is a small browser game built with plain HTML, CSS, and JavaScript. There is no framework or bundler; the only tooling is dependency-free Node tests (`node --test` for pure logic and `tests/harness.js` for simulated DOM/state checks). Changes are made directly in the GitHub repository and the game is played through the site's own link, so no downloadable copy or single-file bundle is produced. The game is centered on a single canvas UI and stores settings in `localStorage`.

The character editor uses a sprite-sheet workflow. The legacy multi-card animation editor was removed; do not reintroduce it. Animation frames are selected, numbered, reordered, cloned, deleted, mirrored, duplicated between movements, and saved in the character database.

## Key files
- [index.html](index.html): canvas, styles, modal editor UI, and DOM structure.
- [storage.js](storage.js): generic `localStorage` helpers (`readStorage`, `writeStorage`, `readJsonStorage`). Load first; everything else depends on it.
- [idiomas.js](idiomas.js) (v0.82): Opções > IDIOMAS (`options_language`, `MENU_LAYOUT.optionsLanguage`) switches PT/EN/ES (`trocarIdioma`, saved as `saiyan_idioma`). The Portuguese text is the key: `T(texto)` looks it up in `IDIOMA_LINHAS` ("PT § EN § ES" per line) and then in `IDIOMA_REGRAS` (regex for texts with numbers/names). Canvas text is translated automatically by `instalarTraducaoNoCanvas(ctx)` (fillText/strokeText/measureText, set right after `ctx` is created in database.js), so drawing code keeps writing Portuguese; `drawBtn` shrinks the font when the text does not fit. HTML (editor, alerts) is translated by `traduzirDom` + a MutationObserver; `#lista-updates` notes stay in Portuguese. Never translate character or attack names. When adding any visible text, add its line to `IDIOMA_LINHAS` (or a rule); `tests/idiomas.test.js` sweeps the screens in EN/ES and fails on leftover Portuguese. Loads right after storage.js.
- [audio.js](audio.js): Web Audio API synth — `initAudio`, `startBGM`/`stopBGM`, `playSound`. No external audio assets.
- [progress.js](progress.js): achievements and the local score ranking (`unlockAchievement`, `saveRankingScore`). Depends on storage.js; calls `playSound` from audio.js at runtime.
- [game-logic-core.js](game-logic-core.js): pure functions with no DOM/canvas dependency (`getWaveParams`, `getDominantMoveAction`, hitbox math, boss attack-pattern selection). Dual-loads as a browser `<script>` and as a Node module — this is what `tests/` exercises with `node --test`. Keep it free of `document`/`canvas`/global game state so it stays testable.
- [conjuntos.js](conjuntos.js): CONJUNTOS DE SPRITES (footer of the editor's ANIMAÇÕES tab, `#conj-area`, two rows: sets on top — gold fixed ORIGINAL button = the character's own animations, blue buttons = groups — and loose forms + AGRUPAR below). A form is "base" or "transf" level N (only the next level after the highest); a group needs 1 base + transformation 1 (later ones optional, in order). `characterDB[k].spriteForms/spriteGroups/spriteActive` ("original" or a group id); the editor works on a copy (`conjTemp`); for an already saved character every change (save form, group, choose, delete) applies at once (`conjPersistir` → `conjAplicarNoPersonagem` + `saveCharacterData`), for a new one on SALVAR PERSONAGEM. Forms already in a group are hidden from the loose row (the group's ✎, `conjGrupoAberto`, shows them). The active group's base idle frame is the card portrait (`conjRetratoUrl`, used by `getCardPortrait`/`getCharacterCardImage` in menu.js) and the editor previews (`conjPreviaAtiva`). The bottom frame strip is empty unless a form is being built/edited (`conjEdicao` swaps `tempAnimations`/`tempFps`; frame buttons call `conjExigirEdicao`; adding a frame starts a new form). Frame row (v0.78): DUPLICAR appends to the target movement (`saveMovementCopy`), CLONAR appends at the end, one outline only (on the box), hold-and-drag reorders (`quadroArraste*`, pointer events; touch after a short hold), and each frame has a padlock (`alternarTravaQuadro`, `tempLoop[state]`, saved as form `loop`, kept in place by `travaRemapear`): the first pass plays every frame, later loops restart at the locked one (`getLoopFrameIndex` in game-logic-core.js; in battle `conjuntoTrava` + time since the fighter entered the move, `p.movimentoDesde` in menu.js). Leaving a form edit (save or cancel/close) closes the group's ✎. Pack frames can be rescaled per move with `escala: {state: [factor, pivotY]}` in the pack JSON, and padlocked with `loop: {variante: {state: frame}}` (Vegeta: transform from the 1st transformed frame, chargeKi from the 4th; read by `conjTravaDaForma`) (Vegeta: transform and diagonal/side flights reduced to the idle size). `tests/editor-quadros-078.test.js`. In battle `getCharacterAnimationFrames` asks `conjuntoQuadros` first: base at level 0, transformation N at level N, staying on the last one. Form images live in IndexedDB (`conjFormaParaSalvar`, read back by `conjuntosAoCarregar`); built-in packs (`CONJ_PACOTES`, e.g. `conjuntos/vegeta.json`: cropped Vegeta sprites, normal + SSJ, seeded once on Vegeta as a blue group via `saiyan_conjunto_vegeta`) load lazily with fetch and each frame is wrapped in a crispEdges SVG (`conjEmbrulharQuadro`, feet on line 103) so it is drawn like the other pixel-art fighters. Loads before database.js. `tests/conjuntos-sprites.test.js`.
- Height (v0.83): each character has `altura` (cm; the editor's `#char-scale` field, now labelled Altura) and each transformation `t.altura`; `getAlturaPersonagem(key, nivel)` (database.js) falls back to `ALTURAS_PADRAO` (official heights of the starting roster, transformations by name) and to the old `scale`. `getFighterBoxSize(key, nivel)` = 52x56 × `escalaDaAltura` (game-logic-core.js: cm/175 clamped to 0.75–1.4); the fight resizes the box on transform keeping the feet (`ajustarCaixaDoLutador`) and the villain's patrol floor follows its height (`world.limitesVilao`). The "i" panel draws each form at its relative height. Pack movements can reuse another's frames (`CONJ_PACOTES[n].usar`, Vegeta back diagonals = flyLeft). `tests/versao-083.test.js`.
- [database.js](database.js): character database, default appearance, sprites/customization data, the sprite-sheet editor, and modal/settings glue code. The starting roster (`DEFAULT_CHARACTERS`) has one ready-made character per builder model in `SPRITE_PRESETS` (the editor's "COMEÇAR A PARTIR DE..." list): when adding a preset, add its character there too (minions are the exception: `minion: <modelo>` classic drawings from minions.js). `seedNewDefaultCharacters` gives existing profiles each new default once (tracked in `saiyan_defaults_seeded`), so a default the player deleted does not come back.
- [gameplay.js](gameplay.js): battle loop, player/boss state, collisions, transforms, waves, particles, and core game mechanics. Character selection (v0.81) happens right before the fight: choosing a stage mode on the map (or VERSUS on the mode screen) calls `abrirTelaPersonagens` (menu.js), which reuses the `characters` state with `selecaoLuta` = "solo" (HERÓIS/VILÕES tabs + LUTAR!, `avancarSelecaoLuta` → `startGame`) or "p1" then "p2" (VERSUS: JOGADOR 1 picks, then JOGADOR 2, the fight starts after P2 confirms; every character listed, `getFilteredCharacters`). Picking asks first (`showSystemConfirm`); in the VILÕES tab a VILÃO-aligned character offers ANTI-HERÓI (play as him) / VILÃO / CANCELAR and an ANTI-HERÓI-aligned one only VILÃO / CANCELAR (`showSystemChoice`, `escolherPersonagemNaSelecao`). From the main menu `selecaoLuta` is null: the screen is titled PERSONAGENS and is view-only — tapping a card or its "i" (`getCharacterInfoRect`) opens `drawCharacterFormsPanel` (base form + every transformation with its name; any tap closes it). A villain drawn from cropped sprites (`lutadorDeSprites`: active sprite group or no builder appearance) is mirrored in `drawPlayerEntity` to face the hero, with left/right fly poses swapped (`trocarLadoDoMovimento`). The single-player villain moves with `stepVilaoPatrulha` (game-logic-core.js: bounces between Y limits without ever getting stuck past them and drifts to a new X in its half). In VERSUS each player stays in their half (`getPlayer1MaxX`/`getPlayer2MinX`). Parry reach is `getParryCircle` (gameplay.js): a circle hugging the ki aura (`entity.auraForma`, measured each frame by `drawKiAura` relative to the fighter box; it grows with the aura when charging/transformed), never below `PARRY_RADIUS`; nothing extra is drawn for it (the sprite's parry pose has its own small shield). The capsule shield bubble uses `auraCaixa` (the rectangle the aura was actually drawn in — the animated aura images are bigger than `auraForma`), always a bit bigger than the aura, so it grows with charging/transformation or any larger aura. The 2-player mode is VERSUS (player 2 controls the rival, best of 3 rounds via `finishVersusRound`/`registerVersusRoundWin`) but is still `gameMode === "coop"` internally (no minions and no pickups there: one against the other on equal terms), because that value is persisted in players' `saiyan_mode`; never show "co-op" to the player. No text pops up in the middle of a fight (`addFloatingText` is only used for the VERSUS round result); picking an item shows a quick drawn icon instead (`{ icon }` entries, `drawPickupFeedbackIcon`: senzu = green +, capsule = shield, cloud = winged sandal, staff = fist). Game-object arrays and timers live in the single `world` object (`world.obstacles`, `world.saibamans`, etc.) instead of separate globals — add new per-run state as a `world.*` property rather than a new bare `let`.
- Saibamans: `createSaibaman`/`stepSaibamanMotion` (game-logic-core.js) move them through `brotar` (rising out of the ground, harmless) → `saltar` (jump up) → `voar`; a flying one that passes within `SAIBAMAN_LUNGE_RADIUS` of the hero switches to `investir` (`shouldSaibamanLunge`/`stepSaibamanLunge`, gives up after `SAIBAMAN_LUNGE_MAX_FRAMES`); on contact gameplay.js sets `agarrar` (hugs the hero's legs from the front for `SAIBAMAN_GRAB_FRAMES`; the hero keeps control but cannot escape — shots don't hit it and `explodeSaibaman` always takes 1 HP, ignoring the shield) and pushes a `world.blasts` effect. Their look (drawn front-facing in a 64x80 space, `traceSaibamanFigure`/`traceCellJrFigure` with the shared `minionLimb`/`minionClaws`/`minionPose`, shown `MINION_DRAW_SCALE` bigger than the hitbox) is cached per pose in menu.js (`getSaibamanSprite`; on the `cell_games` stage `getMinionKind` swaps the drawing for a blue Cell Jr., `traceCellJrFigure`, same mechanic). With one grabbed, charging ki throws it back (`throwSaibaman` → phase `arremessado`, then it flies again and can be shot); PARRY launches it hard forward (`throwSaibaman(s, true)`, `lancadoParry`) and if it hits the villain it explodes there for 1 HP (`explosaoDeSaibaman`); the special destroys a grabbed one (`destruirSaibamansAgarrados`); the hugging one is drawn after the hero (`drawGrabbingSaibamans`), fully opaque. Options > Áudio > TRILHAS SONORAS (`options_tracks`) previews each era's theme via `toggleTrackPreview` (one at a time; `stopBGM` on leaving). Stage music: `getStageMusicEra` maps each stage to its own theme key (field `musica`) and audio.js plays it from `BGM_THEMES` — one original composition per stage (`getBgmTrackList` builds the TRILHAS SONORAS list from `STAGE_PROGRESSION`, lazily since audio.js loads first), each with its own name, meter (`compasso`: 16 or 12 sixteenths per bar), tempo, key and instruments, written in a small text notation (`melodia`/`baixo`/`acordes`, compiled once by `getCompiledTheme`) and scheduled ahead on the audio clock. Keep them clearly different from one another, and never transcribe real songs' melodies (copyright).
- [sprites.js](sprites.js): procedural 2D sprite engine with cel-shaded volume (shading/highlights), built from combinable parts — hair, clothes, tail, wings, back weapon, accessories (see `SPRITE_PRESETS`). Generates fluid per-frame poses for every animation state (`idle`, `flyRight`, `attackKi`, `parry`, `transform`...). Used by `loadDefaultCharacters` (starting roster) and the editor's CONSTRUTOR tab (database.js) to build characters from scratch. No DOM dependency — runs under Node for tests. There is a single drawing style — anime proportions rendered as crisp pixel art; the old "classic" style (and its builder option, migration code and the legacy 8-bit generator) was removed on purpose, so do not reintroduce a style switch. Saved builder characters are always regenerated from their appearance on load. Appearance features are independent of race (`gender`, `earType`, `headFeature`, `bodyMarks`); `spriteLegacyFeatures` converts saves made before that split (detected by a missing `bodyMarks`), so keep new presets explicit about these fields. A character without pants always gets underwear, and a female one with a bare torso gets a top. Script load order in `index.html` matters: `storage.js` → `idiomas.js` → `audio.js` → `progress.js` → `game-logic-core.js` → `sprites.js` → `conjuntos.js` → `minions.js` → `database.js` → `arquivos.js` → `gameplay.js` → `menu.js` → `cenarios3d.js` → `mapa.js` → `arenas.js` → `fases.js` → `atualizacao.js`. (`game-logic-core.js` is pure and dependency-free, so it loads before `database.js`, which already calls `getDefaultTouchHudLayout` and `getAnalogVector` at load time. `sprites.js` is the procedural sprite engine — it generates every character's animation frames from combinable parts; `database.js` uses it in `loadDefaultCharacters` and the character builder.) These are classic (non-module) scripts sharing one global scope, so `let`/`const` declared in an earlier file are visible in later ones, but a function from a later file must not be *called* during an earlier file's top-level code.

The active animation states are `idle`, `flyRight`, `flyLeft`, `flyUp`, `flyDown`, the four diagonal states, `parry`, `attackKi`, `chargeKi`, `transform`, and `special` (v0.79: the special beam pose — `setActionState(caster, "special", 40)` in `triggerSpecialAttack`; it plays once and holds the last frame unless a padlock is set; characters/forms without special frames fall back to `attackKi`; procedural pose in `spritePoseFor`; the Vegeta pack has a 5-frame Galick Ho, cropped from the player's images without repainting; `tests/especial-079.test.js`). Every list of states (`SUB_ANIM_KEYS`, `SPRITE_STATES`/`SPRITE_FRAME_COUNTS`, `CONJ_ESTADOS`, the editor buttons and the DUPLICAR select) must stay in sync.

## Working conventions
- Scale verification effort to the change: a one-line constant, string, comment, or CSS-only color/spacing tweak needs a syntax check and a quick sanity look, not a full browser/responsive pass. Logic, state, or rendering changes still need real verification — see below.
- All responses and communication with the user must be in Portuguese.
- **Every change must exist in the 3 languages (PT/EN/ES).** Any new or changed visible text (canvas, buttons, alerts, editor, achievements, stage/track names, hints) needs its line in `IDIOMA_LINHAS` (or a rule in `IDIOMA_REGRAS`) in [idiomas.js](idiomas.js) in the same PR; when a Portuguese text changes, update its line too (the PT key must match exactly). Only character and attack names stay untranslated, and the `#lista-updates` notes stay in Portuguese. `tests/idiomas.test.js` must pass.
- Keep changes small and localized to the file that owns the behavior. Do not move logic across files without a clear reason.
- Respect the existing naming style in Portuguese and the project’s custom state variables (`gameState`, `selectedCharacter`, `touchHudLayout`, `world`, etc.).
- The game is intentionally static; avoid introducing frameworks, bundlers, or package dependencies unless the task explicitly requires them.
- When editing gameplay behavior that changes logic, state, or rendering, verify the change (in a browser, or with `tests/harness.js` for input/state — see the verification-scaling rule above and "Run and validation" below).
- New pure logic (no DOM/canvas/localStorage) belongs in `game-logic-core.js` with a matching test in `tests/`, so it can be checked with `node --test` before ever opening a browser.
- Keep the canvas logical resolution at `800x350`; responsive behavior is implemented by CSS/viewport scaling, not by changing the game coordinate system. The backing store is sharper (`renderScale`, up to `RENDER_SCALE_MAX` = 2, set by `fitCanvasToViewport` → `setRenderScale`): `canvas` is a Proxy whose `width/height` always read 800x350 (`canvasEl` is the real element) and `applyRenderTransform` (called at the start of every `render` frame) scales the context. Never call `ctx.setTransform(1,0,0,1,0,0)` on the main context — use `applyRenderTransform()`; when copying pixels from the main canvas use `canvasEl` and multiply source coords by `renderScale`. Fighters' pixel art is built at `artW * renderScale` (real screen pixels). Cached scenery layers (360° panoramas, skies, gate/crowd textures, the orbit layers of `drawCachedOrbitLayer`) are made with `c3NovaFaixa` (cenarios3d.js): real-resolution canvas with logical size in `c.__w/c.__h`, rebuilt when `renderScale` changes (`c3Valida`); draw them with their logical size (`c3BlitPanorama`, `c3Img`). Above 1x the canvas CSS uses smooth upscaling (`imageRendering: auto`), so text is not unevenly stretched. During the fight/tutorial `vigiarDesempenho` (menu.js) averages frame times; below ~52 FPS it lowers `renderScaleTeto` half a step (2x → 1.5x → 1x) and never raises it again in the session (`tests/resolucao-automatica.test.js`).
- Fullscreen uses `#game-container`; modals and file inputs must remain descendants of that element so they work in fullscreen.
- Modals (`#modal-editor`, `#modal-updates`, `#modal-alert`) carry `role="dialog"`/`aria-modal` and use `focusModal`/`restoreFocusAfterModal` (in database.js) for focus management, plus a global Escape handler. Keep using those helpers for any new modal instead of toggling `style.display` directly.
- Images the user sends (sprite sheets, references) may be cut out and used in the game as they ask; the user decides about their use.
- The sprite-sheet image remains fixed. Edit frame rectangles instead of adding image panning behavior.
- Preserve frame rectangle positions when changing global frame width/height or spacing. Only selected frames should be moved or spaced.
- FPS changes in the preview are live. Preview frame selection and reorder operations must not mutate the source sprite sheet.

## Planning big requests
- For **big requests** (a new stage or mode, a visual/architecture change across many files, anything that touches performance or many systems at once), first reply with a **short plan in Portuguese**: what will change, which files/systems, how it will look, and the risks (performance on phones, memory). Implement only after the user approves (or adjusts) the plan.
- Small, clear requests (a size/color/text tweak, a single bug fix) go straight to implementation — no plan.
- In batch mode the plan, when needed, comes after "fazer todas as alterações" and before touching code.

## UPDATES (version notes)
- `#lista-updates` (index.html) is a list of versions, newest first, starting from 0.1: a `li.upd-versao` header (`<h3>Versão 0.X (ATUAL)</h3><p>summary</p>`) followed by one `li.upd-item` card per change: `<span class="upd-tag">` + `<strong>title</strong>` + `<p>description</p>`.
- Tags: `upd-novo` NOVO (green) = new in the current version; `upd-corrigido` CORRIGIDO (yellow) = bug fixes; `upd-melhorado` MELHORADO (blue) = improvements to something that existed; `upd-criacao` CRIAÇÃO (gold) = something that did not exist before (older versions).
- One version per merged PR (0.1 = PR #1, 0.66 = PR #66, ...). Each PR adds a new version block on top (next number, marked ATUAL); remove "(ATUAL)" from the previous one and turn its NOVO tags into CRIAÇÃO. The ATUALIZAR button compares this list's text, so every PR must change it.

## Saving tokens (the user pays per use)
- **Batch mode:** when the user says "espera eu falar" (or similar), only note each request in 1–2 lines (a task) — do not open files, run tests or take screenshots. Start everything only on "fazer todas as alterações", then do one test run and one PR for the whole batch.
- **Default verification is economical:** the automated tests plus one quick check of what changed. No screenshots unless the user asks or the change is new visual work (then at most 1–2, viewed once). FPS/stress runs, all-device passes and all-screen sweeps only when the user explicitly asks for them.
- Don't stop to ask for confirmation when the request is clear; ask one single question up front only when a visual request lacks "how it should look" and guessing would likely mean redoing it.
- Keep replies short: a brief summary at the end, not a replay of every step.
- After a PR is merged, suggest starting the next batch in a new conversation (long conversations cost more per message).
- PR flow (the user's choice): after opening a PR, turn on GitHub auto-merge for it (`enable_pr_auto_merge`) so it merges by itself once CI is green; never merge directly. After the merge, reset the work branch to `main` with a force push (`git fetch -q origin main && git checkout -qB claude/repository-verification-pacq7h origin/main && git push -qf origin claude/repository-verification-pacq7h`; allowed in `.claude/settings.json`).

## Run and validation
- Open [index.html](index.html) directly in a browser for quick checks, or serve the folder locally with a simple static server if browser restrictions require it.
- For touch, gamepad, menu, or state-machine logic, `node tests/harness.js .` (or a small script built on it) is usually cheaper and faster than a real browser — it runs the actual game code against a simulated DOM/canvas. Reach for a real browser when the thing being verified is visual (layout, animation, colors, sprite rendering) rather than logical.
- A typical local verification command is:
  - `python -m http.server` from this folder, then open the served page in the browser.
- `game-logic-core.js` has automated coverage: run `node --test tests/game-logic-core.test.js` (Node ≥ 18, no dependencies) after touching wave params, movement-direction logic, hitbox math, or boss attack patterns. This does not replace manual browser verification for anything touching the DOM/canvas/state machines.
- For responsive checks, test the viewport(s) relevant to the change (desktop, ~`375x667`, or fullscreen) and confirm the specific area touched (canvas bounds, modal width, scroll behavior, editor controls, or Database editing). A full pass across all three viewports and all five areas is only required for layout-wide changes (e.g. CSS affecting `#game-container` or the modal shell).
- Browser-side syntax validation can use `new Function(source)` for each JavaScript file when a Node runtime is unavailable; with Node available, `node --check <file>.js` is faster and catches the same class of errors.

## Common pitfalls
- `localStorage` access can fail in some environments; keep writes guarded and avoid breaking the game if storage is unavailable.
- Several systems (audio, UI modals, touch controls, and editor state) depend on global variables and DOM IDs. Prefer matching the existing names instead of introducing new global patterns.
- The canvas and the HTML modal/editor UI are tightly coupled; changes to IDs, event handlers, or global state should be checked against both the markup and the script files.
- The animation editor is intentionally stateful: `tempAnimations`, `savedSpriteMotionPreviewFrames`, `selectedSpriteSheetFrames`, and `spriteFrameRects` must remain synchronized. When a change affects one of them, check its direct dependents (see call sites) rather than re-auditing all four by default.
- The menu backdrop (`drawDragonBallMenuBackdrop`) is drawn once per renderScale into `menuBackdropCache` and copied each frame. `runBackgroundWork` loads up to 4 images per frame.
- Heavy sprite work never runs all at once: procedural animations are lazy getters (`buildProceduralAnimations`), fight-start/transform preloading and pixel-art builds go through `backgroundWork`/`runBackgroundWork` (called once per frame from `render`), the selected fighters (frames, pixel art at the fight size from `getFighterBoxSize`/`ACTION_SPRITE_SCALE`, aura frames) are warmed while in the menus (`warmSelectedFighters`), crisp procedural frames are drawn only as pixel art (`getPixelSvgStub`, no full-size image load), audio is unlocked on the first tap/key, the frame cache is capped (`SPRITE_FRAME_CACHE_MAX`), the builder preview is debounced, and ki-aura frames are cached at one fixed size. `tests/desempenho.test.js` guards these.
- Avoid creating `Image` objects inside the render loop. Use the existing image caches for gameplay, Database cards, and preview frames.
- `player`, `player2`, `score`, `waveNumber`, and `gameState` are still plain globals (not part of `world`) — they're referenced across all three gameplay/menu/database files too pervasively to regroup safely without full browser regression testing. Don't fold them into `world` in a small patch; that's a deliberate, larger refactor for its own PR.

## Preferred edit strategy
- Update UI markup in [index.html](index.html) when the change is visual or adds controls.
- Update generic persistence in [storage.js](storage.js); achievement/ranking rules in [progress.js](progress.js); sound/music in [audio.js](audio.js).
- Update gameplay logic in [gameplay.js](gameplay.js) for movement, combat, waves, collisions, and particle effects. New per-run object arrays or timers go on `world`.
- Update pure/testable helpers in [game-logic-core.js](game-logic-core.js) and add/adjust a test in `tests/`.
- Update menu/input behavior in [menu.js](menu.js) for mouse, keyboard, touch, and HUD interactions.
- Update character defaults, sprite editor, and data storage in [database.js](database.js) when adding new traits, presets, or customization entries.

## Scope for AI agents
Agents should avoid large refactors or broad re-architectures. This project is small and feature-driven, so incremental, targeted edits are preferred. (The storage/audio/progress split and the `world` state grouping were deliberate, narrowly-scoped exceptions done with full syntax checks and, where logic was pure enough, automated tests — not a precedent for open-ended restructuring.)

## Before you finish
Quick checklist, gathered from the rules above — skip any line whose condition doesn't apply to this change:
- Do not hand the user downloadable copies of the files or a single-file HTML bundle; commit and push the changes to the GitHub branch instead.
- Touched wave params, movement-direction logic, hitbox math, or boss attack patterns in `game-logic-core.js`? Run `node --test tests/game-logic-core.test.js`.
- Touched gameplay/input/menu/state logic (not just text/color/comments)? Verify it — `node tests/harness.js .` for input/state, a real browser for anything visual.
- Added or changed any visible text? Add/update its PT § EN § ES line in `idiomas.js` (all 3 languages).
- Touched layout-wide CSS (`#game-container`, the modal shell) rather than one isolated area? Do the full responsive pass (desktop, `375x667`, fullscreen). Otherwise just check the specific area you touched.
